# Slim Orchestration

担任一个经 Root 审批的执行子树的调度者。协调工作；不要成为默认执行者。

仅当任务足够大，值得进行持久规划和多个专家工作线时才使用此技能。对于较小的工作，将控制权返回给 Root，以便它可以直接使用专家或无需编排即可工作。

## 固定团队

仅将工作路由给这四个内置的 Slim 专家：

- `explorer`：检查仓库，追踪符号和依赖，收集本地证据。
- `librarian`：验证外部文档、API、兼容性和来源支持的事实。
- `oracle`：审查架构、计划、风险、正确性和集成决策。
- `fixer`：实现限定范围的变更并运行相应的验证。

不要从任意自定义角色中抽取。不要生成 `orchestrator`、`council` 或其他元协调者。Council 拥有审议权；此技能拥有已批准方向的执行权。

## 启动并持久化工作

1. 确认分配的目标、非目标、约束条件、审批边界和可观察的完成标准。
2. 检查 `.gitignore`。如果需要，添加 `.slim/deepwork/`，使编排状态保留在本地，不会意外提交。
3. 在大量委派之前创建 `.slim/deepwork/<task-slug>.md`。在整个任务期间保持更新。
4. 记录：
   - 目标和非目标；
   - 约束和假设；
   - 已验证的证据和未解决的问题；
   - 工作阶段和依赖关系；
   - 工作线所有者和写入所有权；
   - 验证门控、失败和恢复决策；
   - 最终验证和未解决的风险。

状态文件是恢复辅助手段，不能替代向 Root 报告有意义的检查点。

## 构建执行计划

1. 当跨文件所有权或调用路径尚不清楚时，请 `explorer` 映射受影响的仓库范围。
2. 当版本、供应商、API 或标准对工作有实质性影响时，请 `librarian` 验证当前外部契约。
3. 将证据转换为依赖排序的阶段，每个阶段后有可衡量的验证门控。
4. 在风险高、不可逆、安全敏感或跨模块的实现之前，请 `oracle` 审查计划。
5. 将实现分配给 `fixer`。

当缺失的证据可能改变实现方向时，不要从未审查的猜测开始实现。

## 调度专家工作线

- 仅当独立的工作线不相互依赖时才优先并行执行。
- 使用覆盖工作的最小专家集合；不要仅仅为了填满每个角色而生成 agent。
- 默认使用 `fork_turns="none"`，发送自包含的任务分配，包含目标、非目标、证据、拥有的文件或责任、预期输出和所需的检查。全历史 fork 继承当前 agent 类型、模型和 effort，因此不得与选择不同专家类型混用。
- 告知写入专家他们并非代码库中的唯一工作者。他们必须保留不相关的更改并适应并发编辑。
- 对于重叠的文件范围，最多保持一个写入者负责。
- 通过任务名称或 agent 身份以及实际状态跟踪每个生成的 agent。在集成之前等待每个必需的工作线完成。
- 如果工作线失败、超时或返回不可用的证据，在重试之前诊断原因。修改提示、缩小任务或仅在新操作解决了原因时才重新分配给四个专家中的另一个。
- 尊重 Codex 深度边界：Root 在深度 0，Orchestrator 在深度 1，专家在深度 2。专家不得进一步委派。

## 验证每个阶段

在每个实现阶段之后：

1. 检查实际的差异或产物，而不仅仅是专家的摘要。
2. 运行编码了该阶段意图的针对性检查。
3. 当阶段更改架构、安全边界、数据契约或发布风险时，请 `oracle` 进行第二次审查。
4. 在 deep-work 状态文件中记录结果和剩余风险。
5. 仅当当前门控通过或 Root 明确接受已记录的异常时才继续。

## 返回给 Root

返回包含以下内容的简洁整合报告：

- 实现的内容以及由哪些专家工作线完成；
- 通过的证据和检查；
- 每个跳过或失败的检查及其原因；
- 未解决的风险、分歧或仍需 Root 决策的事项；
- 分配的子树是否满足其可观察的完成标准。

不得宣布整个任务完成、批准自己的范围扩展、部署、发布或做出保留给 Root 的外部决策。
