# Slim Orchestration

担任一个经 Root 审批的执行子树的调度者。协调工作；不要成为默认执行者。

仅当任务足够大，值得进行持久规划和多个专家工作线时才使用此技能。对于较小的工作，将控制权返回给 Root，以便它可以直接使用专家或无需编排即可工作。

## 固定团队

仅将工作路由给这五个内置的 Slim 专家：

- `explorer`：检查仓库，追踪符号和依赖，收集本地证据。
- `librarian`：验证外部文档、API、兼容性和来源支持的事实。
- `oracle`：审查架构、计划、风险、正确性和集成决策。
- `designer`：在设计判断至关重要时，定义或实现视觉和交互工作。
- `fixer`：实现限定范围的变更并运行相应的验证。

不要从任意自定义角色中抽取。不要生成 `orchestrator`、`council` 或其他元协调者。Council 拥有审议权；此技能拥有已批准方向的执行权。

## 启动并持久化工作

1. 确认分配的目标、非目标、约束条件、审批边界和可观察的完成标准。
2. 检查 `.gitignore`。如果需要，添加 `.slim/deepwork/`，使编排状态保留在本地，不会意外提交。
3. 在大量委派之前创建 `.slim/deepwork/<task-slug>.md`。在整个任务期间保持更新。
4. 记录：
   - 目标、非目标、约束和假设；
   - 已验证的证据、未解决的问题，以及已接受的 `librarian` 研究结论（作为已确认的上下文）；
   - 工作阶段、依赖、工作线所有者和写入所有权；
   - 验证门控、Oracle 审查预算、失败和恢复决策；
   - 最终验证和未解决的风险。

`.slim/deepwork/` 目录严格用于进度文件。代码和文档交付物保存到项目路径（`src/`、`docs/`）。

状态文件是恢复辅助手段，不能替代向 Root 报告有意义的检查点。

## 构建执行计划

1. 当跨文件所有权或调用路径尚不清楚时，请 `explorer` 映射受影响的仓库范围。
2. 当版本、供应商、API 或标准对工作有实质性影响时，请 `librarian` 验证当前外部契约。
3. 将证据转换为依赖排序的阶段，每个阶段后有可衡量的验证门控。
4. 在风险高、不可逆、安全敏感或跨模块的实现之前，请 `oracle` 审查计划；当缺失证据可能改变方向时，绝不从未经审查的猜测开始派发。
5. 如果视觉或交互工作至关重要，在分配实现之前获得具体的 `designer` 交接。交接必须说明预期的行为、状态和验收证据。
6. 将实现分配给 `fixer`，或当交付物专门针对视觉或交互时分配给 `designer`。
7. 在派发之前，向 Root 展示一个仅包含以下内容的精简概览：阶段标题和顺序、每个委派专家及其所有权或范围、以及计划的总 Oracle 审查次数（含每个阶段后的门控及其简短理由）。

## 调度专家工作线

- 仅当独立的工作线不相互依赖时才优先并行执行。
- 使用覆盖工作的最小专家集合；不要仅仅为了填满每个角色而生成 agent。
- 默认使用 `fork_turns="none"`，发送自包含的任务分配（目标、非目标、证据、拥有的文件或责任、预期输出、所需检查）。全历史 fork 继承当前类型、模型和 effort，因此不得与选择不同专家类型混用。
- 告知写入专家他们并非代码库中的唯一工作者。他们必须保留不相关的更改并适应并发编辑。
- 对于重叠的文件范围，最多保持一个写入者负责。
- 通过任务名称或身份、范围以及实际状态跟踪每个生成的 agent；在集成之前等待每个必需的工作线完成。
- 如果工作线失败、超时或返回不可用的证据，在重试之前诊断原因。修改提示、缩小任务或仅在新操作解决了原因时才重新分配给五个专家中的另一个。
- 尊重 Codex 深度边界（配置为 `max_depth = 2`）：专家不得进一步委派。

## 验证每个阶段

在派发前根据任务的依赖关系和交付边界规划少量连贯的阶段，并在状态文件中记录阶段顺序和审查门控。在每个计划实现阶段之后：

1. 检查实际的差异或产物，而不仅仅是专家的摘要。
2. 运行编码了该阶段意图的针对性检查。
3. 请 `oracle` 审查阶段结果，作为继续前的自动门控。
4. 在 Oracle 审查之前，将相关已确认的研究结论和文件引用添加到状态文件中，使 Oracle 基于已接受的上下文评估决策，而不是重新做调查。
5. 将重要的可操作 Oracle 结论分诊并批量归入一次有界的修复，然后用聚焦的证据验证；仅当该修复改变了被审查的决策或风险时才请求后续 Oracle 审查。
6. 在状态文件中记录结果和剩余风险。
7. 仅当当前门控通过或 Root 明确接受已记录的异常时才继续。

避免仅为缩小审查范围而创建微阶段。更大、更复杂的任务可以有更宽的阶段、更宽的补丁和相应的更宽的阶段审查。绝不为了重新确认一次机械性的 fixer 变更而增加额外的 Oracle 审查。

## 调度纪律

- 等待每个生成的 agent 达到终态结果后再消费它；当相关工作线仍在运行或终态结果未对齐时，不要进入下一阶段。
- 当一条工作线运行时没有剩余独立工作时，应短暂停止，而不是阻塞或编造结果。
- 在集成之前协调并发写入者之间共享工作树的变更。

## 设计交接护栏

当一个阶段包含 `designer` 时，将交付的 UI/UX 视为后续阶段已接受的设计意图。在继续之前，在状态文件中记录重要的设计决策。

设计工作之后：

- 保留设计意图：布局、节奏、层级、动效、间距、色彩、可发现性、响应式和组件质感；以扎实、自然的措辞改进面向用户的文案，但不改变视觉结构或交互意图；
- 将后续的视觉、响应式、动效、层级、打磨或组件质感变更送回 `designer`；仅在 `fixer` 进行不改变设计的机械性工作时使用它（接线、测试、类型修复、非视觉行为变更）；
- 如果设计意图必须改变，在改变之前记录原因。

## 返回给 Root

返回包含以下内容的简洁整合报告：

- 实现的内容以及由哪些专家工作线完成；
- 通过的证据和检查；
- 每个跳过或失败的检查及其原因；
- 未解决的风险、分歧或仍需 Root 决策的事项；
- 分配的子树是否满足其可观察的完成标准。

不得宣布整个任务完成、批准自己的范围扩展、部署、发布或做出保留给 Root 的外部决策。
